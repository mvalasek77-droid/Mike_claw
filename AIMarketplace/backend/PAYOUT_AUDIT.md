## [1] CRITICAL — account_link return_url/refresh_url cannot return into the iOS app — no URL scheme, no Universal Link, no onOpenURL handler
- **Area:** onboarding  |  **Verdict:** confirmed
- **Location:** backend/src/index.ts:151-156 (refresh_url/return_url = https://aimarketplace.app/payout/...); client opens link via UIApplication.open at MarketplaceStore.swift:522-524; missing handling in App/AIMarketplaceApp.swift and Resources/Info.plist and AIMarketplace.entitlements
- **Money impact:** Creators get stuck and are never paid. After completing Stripe KYC, Stripe redirects the browser to https://aimarketplace.app/payout/complete?account=acct_xxx. The iOS app has NO Universal Link claim (AIMarketplace.entitlements is empty — no com.apple.developer.associated-domains / applinks:aimarketplace.app) and NO custom URL scheme (Info.plist has no CFBundleURLTypes), and AIMarketplaceApp.swift has no .onOpenURL. So the redirect just lands on a web page (or a non-existent page) in Safari; the app is never re-foregrounded and refreshPayoutStatus() (MarketplaceStore.swift:531) is never triggered. payoutConnected stays false, the creator believes setup failed, may retap Connect (compounding the duplicate-account bug above), and the happy path to ever enabling payouts is broken. End state: onboarded-but-not-recognized creators, no payouts.
- **Explanation:** Returning into an iOS app from a Stripe-hosted onboarding flow requires either (a) a Universal Link backed by an associated-domains entitlement + an apple-app-site-association file hosted at https://aimarketplace.app/.well-known/, or (b) a custom URL scheme registered in CFBundleURLTypes (e.g. aimarketplace://payout/complete). Neither exists. The https:// return_url is also not guaranteed to relaunch the app even if it were a valid web page. There is additionally no app-side listener (.onOpenURL on the WindowGroup) to capture the return and call refreshPayoutStatus().
- **Fix:** Pick one deep-link mechanism and wire it end-to-end. Simplest: register a custom scheme in Info.plist (CFBundleURLTypes → CFBundleURLSchemes = ["aimarketplace"]), change the backend to return_url=`aimarketplace://payout/complete?account=${account.id}` and refresh_url=`aimarketplace://payout/refresh?account=${account.id}`, and add `.onOpenURL { url in if url.host == "payout" || url.path.contains("complete") { Task { await store.refreshPayoutStatus() } } }` to the WindowGroup in AIMarketplaceApp.swift. (Universal Links are more robust but require the associated-domains entitlement + hosted AASA file.) Also have the app call refreshPayoutStatus() on foreground as a fallback so status reconciles even if the deep link is missed.

## [2] CRITICAL — Payout has no Stripe-Account header, so the money leaves the PLATFORM's bank, never the creator's connected account
- **Area:** money-direction  |  **Verdict:** confirmed
- **Location:** backend/src/index.ts:224-231 (handleCashOut), compared with the balance read at line 208
- **Money impact:** Platform loses money; creator is never paid from the right balance. Every cash-out wires funds out of the platform's own Stripe balance to the platform's own default bank account. The creator's connected-account balance (the 85% that was transferred via /payouts/transfer) is NEVER touched and NEVER reaches the creator. The platform pays the cash-out amount out of its own pocket on top of having already transferred the creator's share — a double loss — while the creator sees their app balance zeroed (paidOutUSD increments, pendingPayoutUSD set to 0 in cashOut()) but gets no real money. Repeatable for every cash-out.
- **Explanation:** The balance is read scoped to the connected account: stripeGet(`/balance?stripe_account=${account_id}`) on line 208. But the payout on lines 224-231 is created with the plain `stripe()` helper, which sends NO `Stripe-Account` header (the helper at lines 43-57 only sets Authorization with the platform secret key). With no Stripe-Account header, POST /v1/payouts runs against the PLATFORM account and pays out the platform's own available balance to the platform's default external account. The amount is even derived from the connected account's available balance (availableCents from line 209), so the platform pays an amount it computed from someone else's balance, out of its own funds. The read scope (connected account) and the write scope (platform) are mismatched. This is the central money-direction defect: whose bank receives the money is the PLATFORM's, not the creator's.
- **Fix:** Create the payout ON the connected account by passing the Stripe-Account header. Add an optional account parameter to the stripe() helper that sets headers['Stripe-Account'] = accountId, and call it for cash-out: `await stripe('/payouts', { amount: payoutAmount, currency: 'usd', metadata: {...} }, env.STRIPE_SECRET_KEY, account_id)`. Drop the destination field entirely (see separate finding). A payout created with Stripe-Account: acct_xxx draws from that connected account's available balance and sends to that connected account's external bank — which is what the balance read on line 208 already scopes to.

## [3] CRITICAL — stripe() POST helper sets no Idempotency-Key — every /transfers and /payouts retry creates a duplicate money movement
- **Area:** idempotency  |  **Verdict:** confirmed
- **Location:** backend/src/index.ts:43-57 (used by handleTransfer at :267 and handleCashOut at :224)
- **Money impact:** Creator paid twice (overpaid) / platform double-spends. Any transient failure where Stripe actually processed the request but the response was lost (TCP reset, Cloudflare 524/timeout, client retry) results in a second real transfer or payout for the same sale or cash-out. On Workers, fetch() to Stripe can time out or the edge can retry; without an idempotency key Stripe treats the replay as a brand-new charge.
- **Explanation:** Stripe's documented protection against exactly-once money movement is the Idempotency-Key request header: re-sending the same key returns the original result instead of creating a new object. The stripe() helper builds the POST with only Authorization and Content-Type headers and no Idempotency-Key. So /accounts, /transfers (creator earnings) and /payouts (cash-out) are all non-idempotent. /transfers and /payouts are the dangerous ones because they move real money — a retried POST mints a second transfer/payout. The handlers also derive no stable key from the business event (no sale ID, no client-supplied request ID), so even if a key were added there is nothing to key it on today.
- **Fix:** Add an opt-in idempotency parameter to stripe(): `async function stripe(path, body, secret, idempotencyKey?)` and when present set header `"Idempotency-Key": idempotencyKey`. Require callers of money-moving endpoints to pass a caller-supplied stable key. For /transfers, require the iOS client to send a `request_id` (a UUID generated once per sale, persisted) and use it (or a hash of account_id+title_id+amount+saleId) as the key. For /payouts/cash-out, require a client-generated cash-out UUID and use it as the key. This makes Stripe collapse all retries of the same logical event into one transfer/payout.

## [4] CRITICAL — iOS cash-out zeroes the balance and increments paid-out regardless of server result — combined with no idempotency key, retries double-pay
- **Area:** idempotency  |  **Verdict:** confirmed
- **Location:** AIMarketplace/Store/MarketplaceStore.swift:561-590 (cashOut / cashOutRemote)
- **Money impact:** Creator can be paid twice (overpaid) AND the local ledger desyncs. cashOut() fires cashOutRemote in a detached Task then unconditionally does `paidOutUSD += amount; pendingPayoutUSD = 0`. cashOutRemote only print()s http.statusCode and never inspects success/failure. If the server payout fails the app still shows the money as paid out and forgets the pending balance (creator underpaid / loses the balance with no retry). If the network retries under the hood and the payout actually succeeded twice, the creator is overpaid and the app has no record of the duplication.
- **Explanation:** Because the remote POST carries no Idempotency-Key (see stripe() finding) the server cannot collapse retries, and because the client neither awaits nor checks the HTTP result before mutating local state, the local 'truth' (paidOutUSD/pendingPayoutUSD) is decoupled from the actual Stripe outcome. A double-tap is also unguarded: the button is enabled solely on pendingPayoutUSD > 0, and there is no in-flight/isCashingOut flag, so two quick taps both read the same non-zero balance before either zeroes it, firing two /payouts/cash-out POSTs for the same balance. The server's only guard (handleCashOut caps at available balance) does not help across two near-simultaneous requests since both see the same available balance.
- **Fix:** Make cashOut async, add an `@Published private(set) var isCashingOut` guard set true at entry and cleared in a defer, and disable the button while it is true. Only mutate paidOutUSD/pendingPayoutUSD after cashOutRemote returns HTTP 200 and parses a payout id; on non-200 leave pendingPayoutUSD intact and surface an error. Generate a per-cash-out UUID, persist it, and send it to the worker as an idempotency/request id so retries are de-duplicated server-side.

## [5] CRITICAL — cashOut() zeroes pendingPayoutUSD and increments paidOutUSD before (and regardless of whether) the worker confirms — guaranteed accounting drift on any failure
- **Area:** ios-accounting  |  **Verdict:** confirmed
- **Location:** AIMarketplace/Store/MarketplaceStore.swift:561-572 (cashOut) and 574-590 (cashOutRemote)
- **Money impact:** Creator can be silently UNDERPAID. The local books say the money was paid (paidOutUSD += amount, pendingPayoutUSD = 0) the instant the button is tapped, but the actual disbursement is a fire-and-forget Task whose errors are swallowed (catch { print(...) }, lines 587-589). If the network call fails, the worker returns 4xx/5xx, the device is offline, the URL/secret is wrong, or Stripe rejects (e.g. below $1.00 minimum, no available balance), the user's withdrawable balance is destroyed locally while no money ever moved. The funds are now unrecoverable from the app's perspective — pendingPayoutUSD is 0 so they cannot retry, and paidOutUSD overstates lifetime cash-outs.
- **Explanation:** cashOut() mutates local state synchronously and unconditionally: it captures `amount`, fires `Task { await cashOutRemote(...) }`, then immediately does `paidOutUSD += amount; pendingPayoutUSD = 0`. cashOutRemote never reads the response body, never checks http.statusCode (it only prints it), and never calls back into the store to reconcile. So local accounting is fully decoupled from whether Stripe actually paid. There is no rollback, no pending/in-flight state, and no idempotency key, so a user who taps twice (or retries after a perceived failure) also has no protection at this layer.
- **Fix:** Make the local decrement contingent on a confirmed success response. Restructure cashOut to be async: send the request, inspect http.statusCode == 200 AND parse the returned payoutId/status, and only then set pendingPayoutUSD = 0 / paidOutUSD += confirmedAmount. On any non-200 or thrown error, leave pendingPayoutUSD intact and surface the error to the UI. Introduce an explicit in-flight state (e.g. cashOutInProgress) to prevent double taps, and send a client-generated idempotency key that the worker forwards to Stripe so a retry cannot double-pay.

## [6] CRITICAL — App never calls /payouts/transfer — creator's Connect balance is never funded, so cash-out pays from the platform's own balance (platform loses money / wrong party paid)
- **Area:** ios-accounting  |  **Verdict:** confirmed
- **Location:** AIMarketplace/Store/MarketplaceStore.swift:553-556 (addPendingPayout), 987-1011 (grantPurchase); compare backend/src/index.ts:247-285 (handleTransfer) and 202-245 (handleCashOut)
- **Money impact:** Either the creator is NEVER paid for real, or the PLATFORM pays them out of its own funds. On each qualifying sale the app only increments local pendingPayoutUSD; it never calls /payouts/transfer, which is the only endpoint that moves the 85% into the creator's Connect account. When cashOut() runs, the worker's /payouts/cash-out creates a Stripe /payouts against the PLATFORM account (index.ts:224-231, destination 'default'), reading the platform's available balance — not the connected account's. So the creator's Connect balance stays at $0 (real cash-out fails with 'No available balance', 402), while the local books say paid; OR, if the platform account has funds, the platform disburses its own money to the creator's bank with no corresponding transfer ever having been booked against that sale. The 85/15 split exists in two places that are never wired together.
- **Explanation:** The intended flow per the worker is: each sale -> POST /payouts/transfer (moves amount_usd = 85% into the creator's Connect account) -> later POST /payouts/cash-out (Connect account auto-pays to bank). The iOS app implements only the local ledger half (addPendingPayout) and the cash-out call, but grep shows no Swift code ever hits /payouts/transfer. There is therefore no link between a sale and a real Stripe transfer, and cash-out targets the wrong Stripe balance.
- **Fix:** On each qualifying sale in grantPurchase, after computing `earning`, call the worker's /payouts/transfer with account_id = connectAccountID and amount_usd = earning (the already-85% figure) so the creator's Connect balance is actually funded; only credit local pendingPayoutUSD after that transfer confirms. Alternatively, drive the whole ledger server-side and treat the iOS numbers as display-only. Either way, the local pendingPayoutUSD must reflect real Stripe state, and cash-out must target the connected account's balance, not 'default' on the platform.

## [7] HIGH — Repeat /payouts/connect creates a DUPLICATE Connect account every call — no lookup or persistence by email
- **Area:** onboarding  |  **Verdict:** confirmed
- **Location:** backend/src/index.ts:116-163 (handleConnect), reinforced by client at AIMarketplace/Store/MarketplaceStore.swift:496-529 (connectPayout/connectPayoutRemote)
- **Money impact:** Money is mis-routed and can be stranded. Each call to handleConnect unconditionally runs POST /accounts and returns a brand-new acct_xxx. There is no Stripe lookup (no list/search by email) and no server-side store, so the same creator who taps Connect twice (e.g. abandons onboarding, retries, reinstalls, or just double-taps) gets multiple Connect accounts. The platform's /payouts/transfer (line 251) sends the creator's 85% to whatever account_id the CLIENT happens to be holding. If the client's connectAccountID points at account A but the creator finished KYC on account B (payouts_enabled only on B), transfers land in an account that can never pay out — funds sit frozen in a connected account the creator cannot withdraw from, while a fully-onboarded sibling account sits empty. Net: creator underpaid/never paid, platform balance debited, reconciliation impossible.
- **Explanation:** handleConnect has no read-before-create step. There is no Stripe-side dedup either (Stripe does NOT enforce one account per email). The only place the accountId lives is @Published connectAccountID on the iOS device (MarketplaceStore.swift:488), which is overwritten on each connect attempt and lost on reinstall/device-change.

Reuse the account when details_submitted is false so abandoned onboarding can be resumed instead of duplicated.

## [8] HIGH — Created accountId is never persisted server-side; platform cannot independently route transfers or recover from device loss
